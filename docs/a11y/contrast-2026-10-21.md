# Text contrast audit — 2026-10-21

Measured on a local production build (`npm run build && next start -p 3000`), Chrome (Playwright).

## Home buttons, light theme (fixed)

`GradientBorder` paints its inner box `bg-white` in the light theme
(`components/effects/GradientBorder.tsx:50`). The two home buttons kept `text-white` on it.

| Button            | State | Before | After             |
| ----------------- | ----- | ------ | ----------------- |
| Mode Entraînement | rest  | 1.0:1  | 7.1:1             |
| Mode Entraînement | hover | 1.0:1  | 7.1:1             |
| Mode Challenge    | rest  | 1.6:1  | 5.7:1             |
| Mode Challenge    | hover | n/m    | 6.9:1             |
| Dark theme, all 4 | both  | ≥ 6.6  | ≥ 6.6 (unchanged) |

Fix: `text-purple-700` / `text-red-900 hover:text-red-950` in the light theme, `text-white` kept
in the dark theme (`features/home/components/HomeContent.tsx`). Threshold used: 4.5:1 (AA normal
text), stricter than the 3:1 WCAG asks for this 20 px bold text; an intermediate `text-red-800`
gave 3.6:1 on hover and was rejected.

Reproduce (needs a server on port 3000; the default Playwright config targets production):

```bash
npx playwright test tests/e2e/accessibility.spec.ts -g "boutons de" --reporter=list
# with use.baseURL = 'http://localhost:3000' — expected: 2 passed; the ratios are in the
# test annotations (--reporter=json)
```

## Why the existing gates missed it

1. `accessibility.spec.ts` "pas de violations de contraste" keeps only `impact === 'critical'`,
   but axe always reports `color-contrast` as `serious`: that test cannot fail.
2. axe puts text over gradients / `backdrop-filter` in `incomplete` (0 pass, 0 violation) — checked
   on these two buttons. Hence the new helper `tests/e2e/helpers/textContrast.ts`, which measures
   the rendered pixels behind the words (text made transparent, transitions off).

## React #418 on /settings (fixed, 2026-10-21)

Reproduced on every load of a local production build (not a one-off). Cause: `useNotifications`
read `Notification` / `navigator.serviceWorker` in `useState` initializers; the server has neither
and rendered "Non supporte", the browser's first render gave "Non demande". Fix: the browser
values are read after hydration through the shared `hooks/useIsClient.ts`
(`useSyncExternalStore`, the pattern that was copied in `useParticles.ts` and `TourHighlight.tsx`,
now both using the hook). Test: `tests/unit/hooks/useNotifications.hydration.test.tsx` (server
render + `hydrateRoot`, fails on the old code with a recoverable hydration error).
